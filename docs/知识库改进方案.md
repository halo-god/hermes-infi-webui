# 知识库改进方案

> 调研日期：2026-08-06 ｜ 状态：待评审 ｜ 对应代码：`backend/app/` + `frontend/src/`

## 一、现状诊断

### 1.1 底子（已具备的完整链路）

```
上传（魔数校验/大小限制/zip 炸弹防御）
  → 解析（PyMuPDF / python-docx / openpyxl / python-pptx / Docling 后台升级）
  → 分块（500 字符滑窗 / 100 重叠，config.py:193-194）
  → 嵌入（本地 bge-small-zh-v1.5，512 维，零 API 成本）
  → pgvector HNSW 向量索引（migration 0057）
  → 检索（cosine top-5，rag_service.search）
  → 注入 prompt（【团队知识库·检索】段，conversation_service.py:1345-1399）
```

配套：版本快照 + 恢复重索引、Profile 绑定（单条/文件夹/整团队）、chunks 计数端点、Docling 后台升级队列。

### 1.2 断层一：3 个功能级 Bug（知识库"实际不工作"）

| # | Bug | 位置 | 后果 |
|---|---|---|---|
| **B1** | 团队知识库**文件上传后从不建索引** | `app/api/v1/teams.py:568-623` `upload_knowledge` 只落库 + enqueue docling，**没调 `_maybe_index_knowledge`** | 上传的文档 chunks=0，"已索引 N 块"永远 0，RAG 搜不到（对比：JSON 创建端点 L378 和项目文档上传 L705 都索引） |
| **B2** | **Docling 后台升级不重索引** | `agent_runner/runner_docling_upgrade.py:48-56` 用 Markdown 覆盖 `content` 后直接 commit | chunks 停留在 fast-mode 旧文本，与最终 content 不同源 |
| **B3** | **ProjectDoc 向量索引不可达** | `rag_service.is_indexed`（L185-192）只查 `knowledge_id`；`search` 的 `project_doc_ids` 参数从未被调用方传入 | 项目文档永远走 legacy 全文截断注入，向量索引白建 |

### 1.3 断层二：检索质量（"能搜，但搜不准"）

- **纯字符滑窗分块**（rag_service.py:37-64）：无视段落/标题边界；Docling Markdown 的结构在 `_load_plain_content`（L80-82）被拍平
- **chunk 零元数据**：无文档名/页码/标题层级 → 无法溯源、无法过滤
- **无相似度阈值**：top-5 无脑灌，无关内容也进 prompt（`search` L195-236 无 `distance < 阈值` 过滤）
- **无混合检索/重排**：纯向量单路，无 BM25 路、无 rerank
- **注入无出处**：RAG 路径裸文本注入，模型和用户都无法追溯（legacy 路径反而带 `[{entry.name}]`，L1333）
- `is_indexed` 逐条 count（N+1，L1362-1368）

### 1.4 断层三：体验（"能用，但没人知道它存在"）

- **全局错误提示死代码**：`frontend/src/api/client.ts:157` 派发 `hermes:api-error` 但全前端无监听者 → KnowledgeModal/WorkspacePanel 上传失败全部静默
- **知识引用 chip 不可点击**：`ChatView.vue:1200` 无 `@click`（对比普通文件 chip L1205 可打开）
- **Agent 回答无 [1][2] 引用角标**；`markdown.ts:117-122` 的 `postProcessKnowledgeRefs` 因 `<br>` 假设与 `breaks:false` 冲突是死路径
- **RAG 状态零可见性**：`rag_enabled` 默认 false（config.py:190），管理后台无开关/无嵌入模型配置/无状态展示；"已索引 N 块"为 0 时干脆不显示
- **KnowledgePickerModal（带搜索/多选/元数据）整个废弃**，线上用无搜索扁平 picker（Composer.vue:632-647）
- **半成品残留**：KnowledgeModal 随机假 size（L69）、"文件大小留空自动生成"（L131-139）、`window.prompt` 建文件夹（TeamDetailView.vue:174）、解析失败红字无原因无重试

## 二、P0 — 功能修复（半天，让知识库真正工作）

### P0.1 上传端点补索引（B1）

**文件**：`backend/app/api/v1/teams.py` `upload_knowledge`（L568-623）

在 `db.add(k)` / commit 之后、enqueue docling 之前加：

```python
# 立即建索引（fast-mode 提取的 content），与 JSON 创建端点行为对齐
await rag_service.index_knowledge(db, k.id)
```

> 对齐现有模式：`svc.add_knowledge`（team_service.py:416）里的 `_maybe_index_knowledge`。上传端点应复用同一逻辑，避免双实现。

**风险**：低。`_index_content` 幂等、失败静默（返回 0 不影响上传成功）。注意嵌入失败时确保 `processing_status` 语义不误导用户 —— 可结合 B2 修复后的状态处理。

### P0.2 Docling 升级后重索引（B2）

**文件**：`backend/agent_runner/runner_docling_upgrade.py:48-56`

`k.content = md` 之后、`processing_status = "ready"` 之前加：

```python
# content 变了，重建向量索引保持检索一致
await rag_service.index_knowledge(db, k.id)
```

> docling 成功但索引失败的场景：打日志 + chunks-count 自然为 0 可被前端识别；暂不引入新状态。

**风险**：中低。runner 模块 import rag_service 无循环依赖问题（runner 已在用 app.services 的东西）。大文档重嵌入耗时（bge 本地 512 维，千字符文档约数秒）—— runner 任务本身异步，可接受。

### P0.3 打通 ProjectDoc 检索（B3）

**文件**：
- `backend/app/services/rag_service.py`：`is_indexed` 扩展支持 `project_doc_id`（或新增 `is_project_doc_indexed`）
- `backend/app/services/conversation_service.py` `_build_knowledge_prompt_rag`（L1345-1399）：
  - 收集 project_doc_ids（`_collect_folder_knowledge_ids` 已返回两个表的条目，L1160-1217）
  - 按来源类型分别调 `is_indexed`
  - `search` 同时传 `knowledge_ids` + `project_doc_ids`

**风险**：中。`search` 的 `or_()` 里 Python `False` 字面量（L228-229）已存在，扩展时顺手清理为正规条件构造。

## 三、P1 — 检索质量（2-3 天）

### P1.1 chunk 元数据（溯源的基础）

**迁移**：`team_knowledge_chunks` 加列：
- `source_name VARCHAR(255)`（文档名，冗余存，避免 join）
- `page INT` 可空（解析层提供页码时填；Docling 可出页码）
- `chunk_index` 已有

**改造点**：
- `rag_service._split_into_chunks` 返回带元数据的结构（或 `_index_content` 组装时按顺序填）
- `search` 返回值从 `(content, distance)` → `(content, distance, source_name, chunk_index)`

### P1.2 结构感知分块

**方案**：Docling 已产出 Markdown（含 `#` 标题）——分块前按标题切段落组：
- 用标题行（`#`/`##`/`###`）作为自然边界，块内再按 500 字符/100 重叠滑窗兜底
- 标题本身并入其后第一个块（或作为独立小块带 metadata）
- 表格块（docling 的 markdown 表格）整体保留不切

**文件**：`rag_service.py` `_split_into_chunks`（L37-64）加结构感知版本，legacy 纯文本路径（非 docling 来源）保持滑窗。

### P1.3 相似度阈值 + 注入带出处

- `search` 加 `min_score`（settings 加 `rag_min_score: float = 0.35`，bge-small-zh cosine 距离经验值，需实测校准）；无超阈值结果时降级 legacy 注入
- `_build_knowledge_prompt_rag` 注入格式改为：

```
【团队知识库·检索】
[来源: {source_name} · 第{chunk_index}段]
{chunk_body}
```

让模型能引用出处（为 P2.2 的 [n] 角标铺路：模型输出 `[1]` 对应注入顺序）。

### P1.4 可选：BM25 混合检索

- pgvector 无 BM25。低成本方案：`to_tsvector('simple', content)` 存一列 + `websearch_to_tsquery` 关键词路，RRF 融合两路分数
- 或引入轻量检索库。**建议先不做**，P1.1-1.3 已覆盖主要收益；混合检索作为 P3 评估后决定

### P1 验证

- 测试集：构造 10-20 条"问题 → 期望命中文档"用例，比较改造前后命中率（`tests/test_rag_v2.py` 扩展）
- 阈值用真实嵌入实测校准（嵌入 10 条无关查询取距离分布）

## 六、风险与注意

1. **阈值校准**：`rag_min_score` 不能拍脑袋，必须用真实数据分布定；阈值过高会吞掉有效结果（RAG 变"永远 legacy"）
2. **换嵌入模型**：维度写死 512（migration 0057 注释明确），换 bge-base(768) 需重建列 + HNSW 索引 —— P2.3 配置 UI 上应标注此限制
3. **docling 与 fast-mode 双源**：B2 修复后 content 与 chunks 同源，但**旧数据**（历史上传的）需要一次性重索引脚本（可选提供）
4. **`rag_enabled` 默认 False**：本部署 `.env` 已开；P2.3 之前新人部署默认关 → 管理后台开关可避免"开了不知道"的困惑
5. **`docling_enabled` 不存在**：teams.py:593 的 `hasattr` 永远走 else 分支（恒真），顺手在 config.py 加正式字段
